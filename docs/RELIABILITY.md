# SpaceGuard AI — Reliability & Failure Resilience Matrix

> Baseline: Phase 5  
> Architecture: Core Processing vs. Secondary Enrichment

---

## 1. Reliability Philosophy

SpaceGuard AI operates on the fundamental principle of **Graceful Degradation**:
* **Core Operations Must Never Die**: Satellite telemetry ingestion, rule/statistical anomaly detection, evidence generation, and operator dispatch must function even if all external APIs, ML services, and AI engines fail simultaneously.
* **Never Fabricate Data**: If an optional or external dependency fails, the system presents an honest `stale`, `degraded`, or `unavailable` state. It never generates synthetic external space weather, fake ML scores, or hallucinates AI claims.

## 2. Dependency Failure Matrix

| Dependency | Component Class | Failure Mode | System Fallback | User-Visible Behavior | Recovery Behavior |
|---|---|---|---|---|---|
| **MongoDB** | Core Persistence | Connection refusal, timeout, network split | Memory ring buffer preserves last 200 telemetry points and all active anomalies. | Dashboard continues live monitoring. Historical data queries return degraded or cached data. Health reports `database: degraded_in_memory`. | Mongoose automatic reconnection with exponential backoff. In-memory buffer flushed to DB upon reconnection. |
| **Python ML Service** | Secondary Anomaly Detector | Process crash, HTTP 500, timeout (>1.2s) | MLEngine marks `serviceAvailable: false` and throttles retries. Detection pipeline falls back to Rule Engine + Statistical Engine. | Anomalies continue to trigger based on thresholds and z-scores. `mlContribution` is omitted/null. No process crash. | MLEngine retries health probe every 10 seconds. When ML service recovers, hybrid scoring resumes seamlessly. |
| **Gemini AI** | Secondary Explainer | Quota exceeded (429), API outage, timeout (>15s) | Deterministic grounded fallback engine analyzes structured evidence claims and generates a rule-grounded assessment. | Investigation drawer displays structured assessment labeled `Generated by SpaceGuard Grounded Fallback Engine`. Knowns, unknowns, and evidence claims remain grounded. | Live Gemini generation attempts resume on subsequent anomaly investigations. |
| **NOAA SWPC** | Space Context Provider | API timeout (>3s), 5xx error, DNS failure | In-memory cache returns latest valid reading (TTL 2 minutes). If cold start, returns cached snapshot fixture. | Space weather indicator shows `cached` or `unavailable` with timestamp. Never displays fake live storm level. | Background fetch retries on next scheduled interval (5 minutes). |
| **NASA DONKI** | Space Context Provider | API timeout (>5s), rate limit (429), invalid key | Correlation engine queries local MongoDB for previously stored solar flares and CMEs. | Correlation UI shows historical match if within window, or reports `0 external solar events during anomaly window`. | Recovers when NASA API limit window resets or endpoint recovers. |
| **SatNOGS** | Space Context Provider | HTTP timeout (>5s), bad token, endpoint 502 | Serves cached observation records from MongoDB. | Observation list indicates cached/persisted status. | Recovers on next scheduled telemetry pass. |
| **CelesTrak** | Orbital Context Provider | TLE download failure, endpoint unreachable | Precomputed SAA (South Atlantic Anomaly) polygon geometry and cached TLE records used for crossing calculations. | SAA crossing badge shows `SAA crossing (cached TLE)`. | Recovers on next orbital sync schedule. |
| **Socket.IO** | Realtime Delivery | Client disconnection, network packet loss | Frontend state machine switches to `reconnecting`. Client queries REST API for missed state upon reconnection. | UI shows `Disconnected (Reconnecting...)` banner. Re-synchronizes seamlessly without page refresh. | Socket.IO client library performs automatic reconnection with exponential backoff and jitter. |

## 3. Resource Bounds & Safety Limits

| Resource | Enforced Bound | Failure Mitigation |
|---|---|---|
| **HTTP Request Body** | `256 KB` (JSON), `64 KB` (URL-encoded) | Payloads exceeding limit are rejected with HTTP 413 `PAYLOAD_TOO_LARGE`. |
| **Telemetry Ingestion Batch** | Max `2,000` readings per request | Exceeded batches rejected with HTTP 400 `VALIDATION_ERROR`. |
| **Query Pagination Limit** | Max `500` items (default 50) | Queries requesting unbounded limits are clamped or rejected with HTTP 400. |
| **Query Time Window** | Max `30 days` (`2592000000 ms`) | Queries exceeding 30-day range are rejected with HTTP 400. |
| **In-Memory Telemetry Buffer** | `200` readings per satellite | Ring buffer automatically evicts oldest reading on FIFO basis. |
| **In-Memory Anomaly Buffer** | `100` anomalies | Oldest resolved/dismissed anomalies evicted. |
| **Socket.IO Subscriptions** | Max `10` rooms per socket connection | Excessive join attempts rejected with `SUBSCRIPTION_LIMIT_EXCEEDED`. |
| **Socket.IO Connections** | Max `25` concurrent connections per IP | Excessive connections rejected during handshake with HTTP 429. |
| **Rate Limiter Storage** | Sliding window in-memory map with TTL | Expired client records automatically garbage-collected. |

## 4. Disaster Recovery & Process Lifecycle

### Startup Verification
1. Load configuration from `.env` / environment variables.
2. Validate mandatory variables (`PORT`, `CORS_ORIGIN`).
3. Verify optional variables (`MONGODB_URI`, `GEMINI_API_KEY`, `NASA_API_KEY`); log clear warning if missing.
4. Establish non-blocking connection to MongoDB. If unavailable, start in memory-backed degraded mode.
5. Initialize HTTP and Socket.IO servers with Helmet, CORS, and Rate Limiting enabled.

### Graceful Termination
On `SIGINT` (Ctrl+C) or `SIGTERM`:
1. Stop accepting new incoming HTTP connections.
2. Terminate running telemetry simulations.
3. Clear external sync timers and background tasks.
4. Disconnect all active Socket.IO clients.
5. Close MongoDB connection pool cleanly.
6. Exit process with code 0 within a bounded 10-second timeout.
